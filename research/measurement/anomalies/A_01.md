# Observation

Concurrency increased from 1 → 8 (synthetic, 512 input / 64 output, closed-loop, 40 requests) causes throughput to increase only 30% (0.673 → 0.885 rps) and then plateau/decline (4→8: 0.885 → 0.873, -1.4%), while p50 latency increases 9.4× (0.619s → 5.817s), p95 increases 13.2× (0.669s → 8.829s), p99 increases ~13×, and TTFT increases 47× (0.060s → 2.84s). At finer sweep (20 requests, conc 1→16) throughput plateaus at c≈3 (0.862 rps) and remains flat to 16 (0.885 rps), while p50 grows 0.634s → 11.217s (17.7× at c16) and 0.634s → 26.949s (42.5× at c64, 40-req coarse). Token throughput is flat 55–60 tok/s across 1–64. TPOT grows 0.0038s (c1) → 0.1897s (c64, 50×).

In short: beyond concurrency ~3–4, adding concurrency yields <5% throughput gain but 1.5–2× latency/TTFT increase per step, and beyond 8 latency grows ~linear with concurrency.

# Reality Check

- **Realistic:** YES. Concurrency 2–8 is the normal operating range for serving (baseline used 2,4,8). Synthetic 512/64 is a typical short-medium chat prompt (baseline uses same). Closed-loop concurrency is the standard load test for colocated serving. No synthetic trick (no extreme 64k context, no adversarial pattern).
- **Plausible:** The plateau at 3–4 is plausible for a naive CPU server with `asyncio.to_thread` per request and no continuous batching — concurrency beyond threadpool does not increase parallelism but adds queue.
- **Stress-test:** Conc 32,64 are stress-test (above realistic client concurrency for single node), included to show linearity continues; the key observation (4→8 plateau + 1.9× latency) is already at realistic conc8.
- **Synthetic-only risk:** Low. Same pattern appears for chat/rag/agent at 1024/64 conc2 (not shown here but same engine). No prefix/cache trick.

# Preliminary Importance

**High**

- Effect size is very large (tail 9–66×, TTFT 47–271×) and stable across 4 datasets, 3 harness versions, 2 request counts.
- Directly relevant to RQ-1 (P/D vs colocated) and RQ-4 (affinity vs tail) — shows that on a naive server, concurrency alone creates a hot-tail hotspot even without cache affinity, and that adding concurrency beyond ~3 is pure latency cost.
- Challenges the assumption that higher concurrency always improves throughput; quantifies the throughput/latency tradeoff knee at 3–4 for this engine.
- For Stage 3R-C, it provides a concrete, reproducible scaling-failure anchor that must be controlled before testing any affinity or disaggregation hypothesis.
