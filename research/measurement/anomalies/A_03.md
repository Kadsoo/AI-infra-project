# Observation

Resource utilization does not track performance breakdown at high concurrency.

Synthetic 512/64, closed-loop, 40 requests, concurrency 1→64:

- **Throughput:** thr 0.667 (c1, fine 20-req) → 0.885 (c16) → 0.901 (c64) — +35% total, plateau at c≈3 (0.862) then flat ±3% to 64.
- **Tail:** p50 0.634s (c1) → 11.217s (c16) → 26.949s (c64) — 17.7× at c16, 42.5× at c64; p95 0.674s → 17.114s (25.4× at c16) → 39.303s (58× at c64); TTFT 0.063s → 5.328s (84× at c16) → 14.928s (237× at c64).
- **CPU:** mean 45.6% (c1, fine) → 43.0% (c16) → 44.3% (c64) — + -6% to + -? Actually c1 45.6% is highest in fine; in coarse sweepA c1 30.8% → c64 44.3% (+44% relative) but absolute stays 30–46% across 1–64, no 10× increase.
- **RAM:** 16.6GB (c1) → 17.6GB (c64) — +6% (1GB), monotonic but tiny.
- **GPU:** util 0.4% (c1) → 0.06% (c64) flat, mem 20% flat (WDDM desktop, not model).

In short: tail/TTFT explode 17–237× while CPU stays 30–46% (or even decreases from c1 to c2), RAM +6%, GPU flat — no resource saturates as tail explodes. The bottleneck is not visible in standard CPU/RAM/GPU metrics.

Same pattern for output sweep: thr -60% and p50 +3.7× from 16→256, CPU 31%→44% (+42% relative vs 530% tok thr increase) — again sublinear.

# Reality Check

- **Realistic:** YES. Concurrency 4–8 and output 64–256 are realistic. Resource metrics are realistic system signals.
- **Plausible:** For naive CPU server with `asyncio.to_thread`, bottleneck is likely GIL / threadpool queue, not CPU% as measured by `psutil` (which averages over all cores and includes idle). So mismatch is plausible as instrumentation limitation, not hardware limit.
- **Stress-test:** c64 and o256 are stress, but mismatch already at c4 and o64 (realistic).
- **Synthetic-only:** Low risk — same mismatch appears for chat/rag/agent (workload types) where CPU 38–40% flat while thr 0.78–0.81 flat.

# Preliminary Importance

**High (Medium-High if counting engine-specific)**

- Shows that standard CPU/RAM/GPU metrics are insufficient to diagnose tail explosion on this engine — a classic “resource mismatch” that would mislead autoscaling or scheduler decisions.
- For RQ-1/RQ-4, it means that queue hotspot can occur without CPU saturation, so threshold-based scaling on CPU would fail.
- For Stage 3R-C, it mandates adding server-side queue/threadpool instrumentation (active_requests, queue depth, GIL contention) before claiming a GPU/memory bottleneck — otherwise cause is unattributable.
- However, effect is engine-specific (tiny CPU, no GPU); on A100 with vLLM, GPU util would saturate, so importance is to avoid false generalization.
